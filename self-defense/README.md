# go-openapi self-defense

Automated triage of spam issues and pull requests, as a bundled node action:
**no setup steps, no package install, no model download**. The knowledge base
ships inside the action tarball and is on local disk before the first step runs.

> **Status: skeleton.** The storage formats, the text pipeline and the scoring
> algebra are implemented and tested; the signal extractors, rules, GitHub
> client and trainer are typed stubs. Not yet deployable. See
> [DESIGN.md §8](./DESIGN.md#8-implementation-status).

## Usage

```yaml
name: self-defense
on:
  issues:
    types: [opened, reopened]
  pull_request_target:
    types: [opened, reopened]

permissions:
  issues: write
  pull-requests: write

jobs:
  triage:
    runs-on: ubuntu-latest
    steps:
      - uses: go-openapi/gh-actions/self-defense@master
        with:
          shadow-mode: 'true'          # start here — see below
          contact-url: https://github.com/go-openapi/gh-actions/issues
          corpus-token: ${{ secrets.SELF_DEFENSE_CORPUS_TOKEN }}
```

No `actions/checkout`, no `setup-node`, no install step. That is the point: a
spam wave is a latency problem, and every setup step is time the spam is live.

### Start in shadow mode

`shadow-mode: 'true'` evaluates and records but takes no action. Leave it on
until the corpus has enough samples that the trained model earns trust — the
bootstrap knowledge base abstains on everything, so a fresh install has no
opinion about anything and should not be acting on one.

### `pull_request_target`, not `pull_request`

The action needs write permission, and the config must be read from the base
ref. Reading config from the PR head would let an author add themselves to
`trusted.users` in the same PR being evaluated.

## Layout

| path | what |
|---|---|
| [`DESIGN.md`](./DESIGN.md) | architecture of record — read this first |
| `action.yml` | the hot path |
| `train/action.yml` | nightly trainer; opens a PR with a regenerated KB |
| `collect/action.yml` | corpus append; runs in this repo only |
| `src/text/` | redaction, hashing vectoriser, int8 quantisation — implemented |
| `src/scoring/engine.ts` | the log-odds evidence accumulator — implemented |
| `schemas/` | JSON Schema for every on-disk format |
| [`data/corpus/`](./data/corpus/) | shared org-wide corpus (redacted) |
| `data/kb/` | derived knowledge base, regenerated by the trainer |
| `data/trust/trust.yaml` | human-owned trust list, changed by PR |

## Two things worth knowing before reading the code

**Text is redacted before it is ever stored.** URLs become `«url»` with the bare
host kept separately, emails become `«email»`, mentions become `«user»`. A
public repo full of verbatim spam bodies would republish the payload and hand it
indexing. See [DESIGN.md §3.1](./DESIGN.md).

**Signals report facts; the corpus decides what they are worth.** Nothing in
`src/features/` contains a threshold. An extractor reports "account is 3 days
old" and the trained knowledge base says what 3 days is worth this month. That
is the difference between this and a rule engine, and it is why the fitted
log-likelihood ratios live in `kb.json` rather than in code.

## Development

```sh
npm ci
npm run typecheck
npm test
npm run build        # regenerates dist/, which is committed
npm run check-dist   # CI gate: dist/ must match src/
```

Requires node 24. Commits need DCO sign-off (`git commit -s`).
